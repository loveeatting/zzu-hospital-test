# 郑州大学校医院预约挂号系统（Mock 原型）

> 技术验证型原型：用真实的后端服务 + 真实数据库，验证"高校医院预约挂号"场景下最关键的几件事——号源不被超卖、重复预约可控、取消能回滚、并发下数据一致。

---

| 项目 | 内容 |
|---|---|
| 业务场景 | 学生通过小程序预约校医院门诊号，按时段就诊 |

| 数据规模（模拟） | 4 个科室、6 位医生、84 条排班（未来 7 天 × 上午/下午） |
| 技术重点 | 原子扣减防超卖、事务一致性、幂等取消、关联查询 |

一次"预约"请求的完整链路：

```
用户点"确认预约"
  → 小程序 utils/api.js 发 POST /api/appointments
  → FastAPI 用 Pydantic 校验请求体
  → 开启事务：UPDATE schedules SET remain = remain - 1 WHERE id = ? AND remain > 0
  → 判断 rowcount：为 0 则 409 号源已满（并回滚）
  → 插入 appointments 记录
  → 提交事务，返回 {appointment_id, remain}
  → 小程序显示"预约成功，剩余 19"
```

## 3 数据库设计

### 3.1 表结构

```sql
CREATE TABLE departments (
    id       INTEGER PRIMARY KEY,
    name     TEXT    NOT NULL,
    location TEXT
);

CREATE TABLE doctors (
    id            INTEGER PRIMARY KEY,
    department_id INTEGER NOT NULL REFERENCES departments(id),
    name          TEXT    NOT NULL,
    title         TEXT,             -- 职称
    specialty     TEXT              -- 擅长
);

CREATE TABLE schedules (
    id         INTEGER PRIMARY KEY,
    doctor_id  INTEGER NOT NULL REFERENCES doctors(id),
    date       TEXT    NOT NULL,    -- ISO 格式 YYYY-MM-DD，便于排序比较
    period     TEXT    NOT NULL,    -- 上午 / 下午
    start_time TEXT,
    end_time   TEXT,
    room       TEXT,
    capacity   INTEGER NOT NULL,    -- 总号源
    remain     INTEGER NOT NULL,    -- 剩余号源（关键字段）
    UNIQUE (doctor_id, date, period)
);

CREATE TABLE appointments (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    schedule_id  INTEGER NOT NULL REFERENCES schedules(id),
    patient_name TEXT    NOT NULL,
    phone        TEXT,
    status       TEXT    NOT NULL DEFAULT 'BOOKED',   -- BOOKED / CANCELLED
    created_at   TEXT    NOT NULL
);

CREATE UNIQUE INDEX ux_appt_active
    ON appointments (schedule_id, patient_name)
    WHERE status = 'BOOKED';
```

### 3.2 三个设计决策及理由

**决策 1：`remain` 独立存储，而不是"用 capacity − 预约数"临时计算。**
因为扣减必须是一条原子 SQL。如果每次读取时才算，就无法用 `WHERE remain > 0` 一次性完成"判断 + 扣减"，并发下必然超卖。

**决策 2：`date` 存 ISO 字符串 `YYYY-MM-DD`。**
字符串按字典序排序即等价于按时间排序，SQLite 中 `ORDER BY date` 直接可用，前后端传输也无歧义。

**决策 3：取消只改状态、不删记录。**
医疗场景必须留痕（谁在何时取消了哪个号）。配合"部分唯一索引"，`CANCELLED` 记录不再占用唯一性约束，同一患者可重新预约。

## 5 五个核心技术点

### 5.1 防超卖：把"判断"和"扣减"合并成一条 SQL

**问题**：直觉写法是"先查余号 → 判断 > 0 → 再扣减"。两个人同时操作时，可能都读到剩余 1 个号，都判定可以约，于是卖出 2 个，`remain` 变成 -1。

**方案**：

```sql
UPDATE schedules SET remain = remain - 1 WHERE id = ? AND remain > 0
```

再检查影响行数：

```python
if cur.rowcount == 0:
    raise HTTPException(status_code=409, detail="号源已满或排班不存在")
```

**为什么有效**：UPDATE 是一条语句，数据库保证其原子性；两个并发请求不可能同时"条件成立"。`rowcount` 就是"这次扣减是否真的发生了"的唯一权威。

### 5.2 事务一致性：扣号和写记录同生共死

```python
with conn:                      # 进入事务
    cur = conn.execute("UPDATE schedules ... AND remain > 0")
    if cur.rowcount == 0:
        raise HTTPException(409, ...)   # 触发回滚
    conn.execute("INSERT INTO appointments ...")
```

任何一步失败，另一句自动回滚，不会出现"号扣了但没生成预约"的幽灵数据。

**一个容易踩的坑**：捕获 `sqlite3.IntegrityError` 的位置必须在 `with` **之外**。如果写在 `with` 内部，事务会认为"没有异常"而提交，导致号被扣、预约却没写进去。

### 5.3 重复预约防护：部分唯一索引

```sql
CREATE UNIQUE INDEX ux_appt_active
    ON appointments (schedule_id, patient_name)
    WHERE status = 'BOOKED';
```

同一个人对同一排班只能有一条有效预约。冲突时数据库抛 `IntegrityError`，代码转成 409。

选"部分索引"而不是"普通唯一索引"的原因：取消后状态变为 `CANCELLED`，该记录不再受约束，患者可重新预约同一号源——业务上更合理，且不需要在代码里判断。

### 5.4 取消预约：幂等 + 号源回滚

```python
cur = conn.execute(
    "UPDATE appointments SET status = 'CANCELLED' WHERE id = ? AND status = 'BOOKED'",
    (appointment_id,),
)
if cur.rowcount == 0:                 # 已经取消过 / 不存在
    raise HTTPException(409, "该预约已取消，无需重复操作")

conn.execute(
    "UPDATE schedules SET remain = remain + 1 WHERE id = ? AND remain < capacity",
    (row["schedule_id"],),
)
```

两个要点：
1. **状态翻转本身就是"抢占"**：只有把 `BOOKED` 改成 `CANCELLED` 成功（`rowcount = 1`）的那次操作才允许退号，重复取消无法二次退号；
2. **`AND remain < capacity` 是兜底**：即使逻辑出错，余号也永远不会超过总号源。

### 5.5 关联查询：三表 JOIN 拼出"我的预约"

`appointments` 只存 `schedule_id`，但页面要显示医生、科室、时段、诊室。用一次 JOIN 全部取回：

```sql
SELECT a.id, a.status, a.created_at,
       s.date, s.period, s.start_time, s.end_time, s.room,
       d.name AS doctor_name,
       dep.name AS department_name
FROM appointments AS a
JOIN schedules   AS s   ON s.id = a.schedule_id
JOIN doctors     AS d   ON d.id = s.doctor_id
JOIN departments AS dep ON dep.id = d.department_id
WHERE a.patient_name = ?
ORDER BY a.id DESC
```

价值：数据不重复存储（医生名只在 `doctors` 里存一份），用的时候按需拼接，避免更新遗漏。

## 6 并发压测结果

### 6.1 测试方法

`test_concurrent.py`：用 `threading.Barrier` 让 N 个线程在同一瞬间发起预约请求（Barrier 保证所有线程到齐后才同时出发，制造真实竞态窗口），统计成功/失败数量，并断言最终数据。

### 6.2 三组实测结果

| 场景 | 并发线程 | 可用号源 | 成功 | 号源已满(409) | 最终 remain | 结论 |
|---|---|---|---|---|---|---|
| 20 人抢 1 个号 | 20 | 1 | 1 | 19 | 0 | 只卖出 1 个 |
| 50 人抢 3 个号 | 50 | 3 | 3 | 47 | 0 | 只卖出 3 个 |
| 30 人抢 20 个号 | 30 | 20 | 20 | 10 | 0 | 只卖出 20 个 |

耗时约 0.4~1.1 秒，全程无负值、无超卖、无 `database is locked`。

### 6.3 判定逻辑（脚本内断言）

```python
if final < 0:                          → 失败：remain 变成负数
if len(ok) > remain_n:                 → 失败：成功人数 > 可用号源
if final != remain_n - len(ok):        → 失败：余号不等于"初始 − 成功"
if other:                              → 失败：有请求未正常返回
```

第三条最严格：要求 `remain` 精确等于"初始号源 − 成功人数"，任何多卖或多退都会被发现。

## 8 常见提问与参考回答

**Q1：为什么不用"先查询余号再判断"的写法？**
A：并发下两个人可能读到同一个余号，都判断通过，导致超卖且余号变负。改成条件更新（WHERE remain > 0）后，判断和扣减在数据库内部一次完成，用 rowcount 判断成败，天然互斥。

**Q2：SQLite 能扛住并发吗？生产环境怎么办？**
A：SQLite 写操作是全库锁，适合原型和演示；本项目通过"单条短事务"把锁持有时间压到毫秒级，20~50 并发在本地验证无异常。生产环境换 PostgreSQL/MySQL，同样的条件更新语句依然成立，只是锁粒度从库级降到行级。

**Q3：取消为什么要用 UPDATE 而不是 DELETE？**
A：医疗场景需要留痕（审计）。保留记录并改状态，既能追溯，又能通过"部分唯一索引"允许患者重新预约。

**Q4：怎么保证取消不会被重复退号？**
A：状态翻转语句带 `AND status = 'BOOKED'`，第二次执行 rowcount 为 0，直接 409，退号语句不会被执行；另外退号语句还有 `AND remain < capacity` 兜底。

**Q5：如果用户提交预约后网络断了，号会被扣掉吗？**
A：会扣掉，因为请求可能已经到达服务端并成功。这属于"预约成功但用户没看到结果"，可通过"我的预约"列表弥补；更完善的方案是加入超时未支付自动取消（见第 9 节）。

**Q6：怎么防止一个人把所有号都占了？**
A：当前用"同一排班同一姓名限一条有效预约"（唯一索引）。生产环境应按学号/身份证 + 每日限额约束，并加实名认证。

**Q7：小程序为什么不能直接用 Python 写？**
A：微信小程序的视图层是 WXML/WXSS，逻辑层是 JavaScript，官方不支持 Python。Python 只能做后端服务。

**Q8：前后端怎么联调的？**
A：小程序用 `wx.request` 请求本地 `http://127.0.0.1:8000`，开发者工具中勾选"不校验合法域名"即可；真机调试时改为电脑局域网 IP，后端用 `--host 0.0.0.0` 启动。

**Q9：为什么文档页 `/docs` 要自定义？**
A：FastAPI 默认文档页从境外 CDN（cdn.jsdelivr.net）加载 Swagger UI 资源，国内网络不可达会显示白屏。改为自建路由 + 国内 CDN 后恢复正常。

**Q10：这个原型离真实上线还差什么？**
A：见第 9 节——鉴权、真实号源规则、支付/退费、消息通知、超时释放、日志审计、HTTPS 域名与备案。
